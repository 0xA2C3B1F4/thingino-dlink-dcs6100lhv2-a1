# September 24 Raptor `867d1182` installation on the first A1 camera

This record applies to source `867d1182aa2f3586ce35d6709f51463faff010bb`
and signed universal bundle SHA-256
`17e7f3fdaa78b26a49f3dd5c5776d409c525d72a217ea1a2ac496ca7d875c1c4`.
The target was the first DCS-6100LHV2 A1 camera on the local LAN. Its
same-camera identity binding is retained in the private installation evidence.
The build run `build-20260924T091635119616Z-867d1182aa2f` produced two
byte-identical clean complete-firmware builds. Its `reproducibility.json`
reports `scope: complete-firmware`, `builds: 2`,
`component_cache_used: false`, `inspections_accepted: true`,
`differences: []`, and `byte_identical: true`; that report's SHA-256 is
`459e9f3d19bb85f469c6b6264786e7060ca87701cecdbb57892fcf32d0525987`.

The repository's `scripts/release_closure.py` independently validated this
completed run against the universal signing public key, install set, final
root, Raptor component and source locks. Two runs produced byte-identical
`candidate-closure.json` and `notice-manifest.json` files. Their respective
SHA-256 values are
`18dd2e39be32c8bbe6ef28416e4d2ec571de38f16ecb9ebf4fb4552012fea16b`
and `220b8eecb2bc8cf6a34566c1bb1ab5acdd1ac17a568a1de9554b2c1d4c43904f`.
The closure binds the signed bundle digest above to source `867d1182` and the
current Raptor source lock. These private host-side sidecars mark legal review
`not-assessed` and redistribution `not-authorized-by-this-repository`; they do
not approve firmware publication or prove the physical installation.

Passive UART captured the stock updater's exact completion line:
`Update DCS6100LHV2Ax_FW000B00_THINGINO_SD.bin successfully, remove the SDcard and restart`.
Stage 1 then recorded `recovery_checkpoint_committed`,
`stock_userdata_backup_committed`, `provisioning_data_written_and_verified`,
`final_system_written`, `final_kernel_tail_written`,
`preactivation_kernel_verified`, `activation_written_and_verified`,
`camera_install_files_passivated`, `sd_unmounted`, and `rebooting_final`.
The following boot reached `thingino_verified_switch_root`. The private UART
capture `uart-stock-updater-20260924.log` has SHA-256
`d5758d15c839ad887fa0a1864a02df05cbabab2adadb44c5ed3f30d02322d23f`;
the raw capture is not part of this repository.

The supported `universal verify` and separate `universal verify-readback` both
passed on September 24 for this bundle and camera. The selected readback
covered logical partitions 0, 1, 3, 5, and 6. It was not a whole-flash
comparison: mutable data and an exact physical mtd2 comparison remain outside
this evidence.

Before a cold reboot, the authenticated Chromium Time page showed `Etc/GMT`,
the default internet NTP pool and an August 6 camera date. The operator saved
a numeric LAN NTP server through the UI; Settings reported it saved. Pinned
SSH readback confirmed the server in `/etc/default/ntp.conf` and the timezone.
One UI `Sync time now` action reported `Time synchronized`. A same-time read
showed both host and camera at `2026-09-24T11:33:38Z`. Reloading the Time page
after that clock step kept the Chromium session authenticated. A first login
after the previous boot had shown `Failed to fetch`; browser Reload recovered
it. The cause of that transient failure is unknown.

The operator then cold power-cycled the camera with the card installed. The
private passive UART capture has SHA-256
`58ae41ce4b4de75f7203e3839b2cdd9253fac64f6986543fc63c65f5812b6e31`.
It showed Stage 1 boot, `device_verified`,
`thingino_verified_switch_root`, LAN readiness and HTTPS startup, with no
installer write phase. At the first post-network sample, host UTC was
`2026-09-24T12:29:54Z` while the camera still showed August 6. At the next
sample, 57 seconds later, host UTC was `2026-09-24T12:30:51Z` and camera UTC
was `2026-09-24T12:30:52Z`. The clock therefore corrected automatically within
the five-minute observation bound, without a manual sync after boot. The NTP
server and timezone persisted. `/etc/resolv.conf` was empty and only the subnet
route was present, consistent with use of the numeric LAN server.

After that cold boot, Chromium Preview reached Live WebRTC on Main stream. The
camera microphone began Off. The operator switched it On and pressed Listen
once. Chromium showed `Audio playing` and increasing received-audio packet
counts; the operator heard audio immediately, without Reload or a second
Listen press. On Substream, Preview again reached Live WebRTC with the camera
microphone still On. One Listen press showed increasing received-audio packet
counts, and the operator heard audio immediately. A separate Substream check
began with the camera microphone Off and Live WebRTC video. The operator
switched the microphone On and pressed Listen once. Chromium showed
`Audio playing`, and the operator heard audio immediately without Reload or a
second press. After the checks, Listen and the camera microphone were both
switched Off; the UI confirmed each toggle at value `0`. This is a bounded
Chromium playback check on the installed `867d1182` bytes after the cold boot.

After the clock correction and playback checks, Chromium's `Log out` action
showed `You have been signed out` and the login form. Reload kept the login
form visible; the browser did not automatically sign in again. This confirms
the observed browser logout flow, not server-side token revocation. Natural
session expiry remains untested, so the local clock and session acceptance
ledger gate stays blocked.

Rights and legal review, installation on the second camera, and the full
candidate matrix also remain open. This installation does not establish public
firmware-release readiness.
