## September 25 bounded runtime and RTSP follow-up

After the operator powered on the same camera, strict SSH host authentication
matched the server public key independently derived from the saved provisioning
package for this installation. The matching provisioned client identity then
authenticated. No firmware, configuration or service lifecycle changes were
made. The ready marker contained `started` and all 11 recorded service PIDs
were alive. Local snapshot requests for channels 0 and 1 returned HTTP 200
with 91058 and 13610 bytes respectively. Snapshot decoding was not checked.

The repository's `installer.rtsp_verify.verify_rtsp_h264_dimensions` was run
sequentially for `/stream0` at 1920x1080 and `/stream1` at 640x360, using the
provisioned, domain-separated viewer credential and a 15-second bound per
stream. Both checks passed: unauthenticated OPTIONS returned RTSP status 401,
Digest authentication succeeded, and interleaved TCP delivered
SPS dimensions matching the expected stream, a complete IDR and two RTP
timestamps. The main stream yielded 26 packets and the substream 8 packets
before their checks completed. Connections were closed afterward.

This is bounded RTSP authentication and H.264 framing evidence, not an external
decoder test, RTSP audio acceptance, long-running stability, ONVIF acceptance
or a repeat of the full installation readback. Private access provenance,
boot identity and executable hashes are retained in
`access-runtime-20260925.private.md` with the installation evidence.

The subsequent ONVIF check used direct LAN HTTPS with certificate and hostname
validation. The camera certificate was obtained through the pinned SSH channel;
no TLS verification bypass was used. Unauthenticated Media1 `GetProfiles`
returned HTTP 401 with a SOAP fault. A fresh WS-Security UsernameToken digest
returned HTTP 200 and exactly `Profile_0` and `Profile_1`. Authenticated
`GetStreamUri` and `GetSnapshotUri` succeeded for both profiles, advertising
the camera's LAN address with `/stream0`, `/stream1`, `/onvif/image.cgi` and
`/onvif/image1.cgi` as appropriate. None of those URIs contained userinfo or
query parameters. The boot ID was unchanged across these requests.

Both advertised snapshot endpoints then accepted HTTP Digest authentication
over the same verified HTTPS connection setup. They returned HTTP 200 with
93235 and 13840 bytes. Pillow fully decoded each JPEG and confirmed 1920x1080
and 640x360 dimensions. Images were held in memory and were not saved.
These results cover Media1 profile/URI reads and snapshot delivery, not
WS-Discovery, Media2, ONVIF setters, event subscriptions or full conformance.

## September 25 server-side logout check

A separate test session used direct LAN HTTPS with the same pinned-certificate
and hostname validation. `GET /api/v1/config/time` without a session returned
401. A normal login returned 200 with `success: true`; the issued cookie had
Secure, HttpOnly and SameSite=Strict attributes. The protected read then returned
200 with that cookie. `POST /api/v1/auth/logout` returned 204, and deliberately
replaying the original cookie against the same protected read returned 401.
The boot ID remained unchanged. The test did not reuse the operator's browser
session, change settings or retain credentials/cookies on disk. This closes
the previously untested server-side revocation observation, not natural
12-hour idle or 24-hour maximum session expiry.

A subsequent resource snapshot at uptime 885 seconds found Control at 2192 KiB
RSS, 16 threads and five file descriptors. All 11 supervisor PID paths had
readable process status. A bounded kernel-log search found no matches for
OOM-killer, out-of-memory, segfault, kernel panic, or IMP/ISP error patterns.
These are single-time observations, not proof of resource stability or absence
of all kernel/media errors. The full resource/concurrency gate remains open.

## September 25 MJPEG retry and bounded client disconnect check

A separate authenticated session fetched `/media/v1/mjpeg` over verified LAN
HTTPS for streams 0 and 1, with each of the Preview revisions `q=50` and `q=51`.
All four requests returned HTTP 200 multipart responses. Two JPEG frames per
request decoded successfully at 1920x1080 or 640x360 as appropriate. The
`q=51` authorization failure observed on the older September 23 candidate did
not recur in this direct-endpoint check. This does not replace browser fallback
and Reload interaction acceptance. Frames and session credentials stayed in
memory; the connections closed and the test session logged out afterward.

A further bounded probe opened one MJPEG connection per stream, read their
HTTP 200 headers, and left their bodies unread. Three protected configuration
reads during that interval all returned 200 in 0.427, 0.272 and 0.259 seconds.
After explicitly closing both response streams and waiting three seconds,
another protected read returned 200. The boot and sampled process IDs stayed
unchanged. Control had 16 threads and five FDs before, during and afterward;
RHD threads were 1→3→1 and FDs 9→11→9. Control RSS was 2172→2392→2392 KiB,
and RHD RSS 1636→1660→1660 KiB. Those retained allocations are not evidence of
a leak or of long-term stability. The probe covers two short unread clients
and disconnect cleanup, not prolonged backpressure or broad load acceptance.
